# Phase 4.1: App.tsx Refactor - Context

**Gathered:** 2026-06-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Reduzir App.tsx de 623 para <200 linhas extraindo hooks de fluxo restantes. Três hooks já foram extraídos (useAppShell, useLeagueManager, useBracketManager) — App.tsx está em 343 linhas. Faltam ~143 linhas para a meta.

Este refactor extrai a lógica de negócio restante do App.tsx mantendo o render inline como screen router natural. O objetivo é saúde de código, não extração cega.
</domain>

<decisions>
## Implementation Decisions

### Estratégia de hooks
- **D-01:** Manter `useAppShell` como está (28 linhas — screen, matchContext, tournamentMode, isTournamentEntry, goHome, handleContinueTournament)
- **D-02:** Extrair `useGameFlow` — fluxo de partida única: handleTeamsSelected, handleStartMatch, handleViewStats
- **D-03:** Extrair `useOnlineMatch` — fluxo de partida online: handleStartOnlineMatch, handleOnlineMatchResult, onlineRngRef
- **D-04:** Extrair `useResumePrompt` — estado e handlers do prompt de resume (resumePrompt, handleResumeContinue, handleResumeNew, useEffect Escape)
- **D-05:** NÃO extrair useAppNavigation separado — useAppShell já cobre navegação básica; resume prompt fica em hook próprio

### Função render
- **D-06:** Manter inline no App.tsx — App.tsx é o screen router natural. Extrair para AppRouter adicionaria 15+ props ou contexto sem ganho arquitetural. 181 linhas estimadas bate a meta de <200 com folga.

### Claude's Discretion
- Dependência entre hooks: manter flat-passing a partir do App.tsx (padrão já usado por useLeagueManager e useBracketManager)
- useGameFlow recebe: setScreen, setHomeTeam, setAwayTeam, setMatchContext, setIsKnockout, setGameMode, matchContext, isTournamentEntry, setIsTournamentEntry, isKnockout, leagueState, bracketState, setLeagueState, setBracketState, gameMode, homeTeam, recordH2H, evaluateAchievements, setLastResult
- useOnlineMatch recebe: setScreen, setHomeTeam, setAwayTeam, setMatchContext, setIsKnockout, recordH2H, evaluateAchievements, setLastResult, peer
- useResumePrompt recebe: leagueState, bracketState, setScreen, setTournamentMode, setLeagueState, setBracketState
- evaluateAchievements callback fica no App.tsx como wrapper fino (6 linhas)
- handleTournamentStart dispatch fica no App.tsx (5 linhas)
- handleViewStatsFromMatch routing fica no App.tsx (10 linhas)
- handleLeagueFromHome + handleCupFromHome ficam no App.tsx (10 linhas)
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `useAppShell` — screen/mode state manager já extraído, usado como referência de pattern
- `usePersistedState` — hook interno usado por useLeagueManager e useBracketManager para localStorage
- `useMatchHistory`, `useH2H`, `useAchievements` — hooks já consumidos pelo App.tsx, permanecem como estão

### Established Patterns
- Hooks recebem dependências via objeto params (`{ setScreen, setHomeTeam, ... }`)
- Hooks retornam `{ state, setState, handlers }` desestruturados
- Hooks que persistem usam `usePersistedState` com callback `onPersist: notifySave`
- Callbacks são definidos com `useCallback` e dependências explícitas

### Integration Points
- App.tsx é o único ponto de integração — todos os hooks se conectam aqui
- `handleStartMatch` atualiza leagueState/bracketState se `matchContext === 'league'/'bracket'` (será absorvido por useGameFlow)
- `handleViewStatsFromMatch` faz dispatch condicional (league → handleLeagueMatchResult, bracket → handleBracketMatchResult, regular → handleViewStats)
</code_context>
