# Phase 4.4: Modo Carreira - Research

**Researched:** 2026-07-24
**Domain:** Client-side React state architecture, persistence design, procedural player generation reuse (no new external dependencies)
**Confidence:** HIGH (all core findings verified directly against this repo's source and empirically benchmarked; no third-party library research was needed — this phase is pure internal architecture)

## Summary

Modo Carreira does not require any new library, API, or infrastructure — it is entirely an internal state-architecture problem layered on top of code that already exists and already works (`LeagueState`, `BracketState`, `generatePlayer()`, `usePersistedState`, `useLeagueManager`/`useBracketManager` as the hook pattern to imitate). The single biggest technical risk named in CONTEXT.md (D-03: recalculating thousands of players across 6 leagues every season transition might be too slow for the browser) was empirically benchmarked in this research session and found to be a **non-issue at current data scale**: recalculating attributes for all 2,052 players across the 6 leagues (114 teams × 18 players) takes ~1.2ms, and serializing the resulting persisted career object (with all 6 leagues' evolved rosters embedded) takes ~1.5-2ms. Eager, synchronous, whole-league-set recalculation at every season transition is safe and simpler than building lazy/staleness-tracked incremental recalculation — the latter remains a reasonable Claude's-Discretion choice for future-proofing, not a performance necessity today.

The two areas needing real design care are (1) **persistence key isolation** — the career save must live at a wholly new localStorage key (not `fp:leagueState:{id}` or `fp:bracketState`, both of which are actively used and singly-scoped by today's Campeonatos/Copas modes) — and (2) **hook/state wiring** — `useGameFlow.ts` and `App.tsx`'s match-result routing are hardcoded around exactly two state slots (`leagueState`, `bracketState`) and a `MatchContext` union that has no career-aware value yet. Both are solvable with patterns already present in the codebase (adapter setters matching `Dispatch<SetStateAction<T>>`, extending the existing discriminated-union style), but every hook file (`useAppShell.ts`, `useLeagueManager.ts`, `useBracketManager.ts`, `useGameFlow.ts`, `useResumePrompt.ts`) currently redefines its own local copy of the `Screen`/`MatchContext` union types rather than importing a shared one — this is a real, TypeScript-silent risk when adding new screen/context values for career mode (see Common Pitfalls).

**Primary recommendation:** Build `useCareerManager` as a new hook following the exact `useLeagueManager`/`useBracketManager` shape (params-object in, `{state, setState, handlers}` out), persisted as a single new key `fp:career` holding a `CareerState` wrapper that embeds `LeagueState`- and `BracketState`-shaped season data plus per-league evolved rosters for all 6 leagues. Reuse `generatePlayer()`'s `base = ovr - 7` / `spread = min(10, floor(ovr/8))` formula as the mechanism CONTEXT.md's D-02 already points to, but decide explicitly (this is a real fork in the design, not just an implementation detail) whether progression re-rolls a player's attributes from scratch toward a new target OVR (what D-02's wording literally suggests) or nudges existing attributes proportionally toward the new target (preserves individual attribute "shape" — a fast winger stays fast) — see Code Examples.

### Pattern 1: Hook shape for `useCareerManager` (mirror existing managers)

**What:** Follow `useLeagueManager`/`useBracketManager` exactly — params object of shared setters/callbacks in, `{state, setState, handlers}` out, persisted via `usePersistedState`.

**When to use:** This is the entry point for all career logic; `App.tsx` wires it exactly like the other two managers.

**Example (grounded in actual `useLeagueManager.ts` signature, lines 15-33):**
```typescript
// Source: src/hooks/useLeagueManager.ts (pattern to mirror)

  setScreen: (s: Screen) => void;
  setHomeTeam: (t: Team) => void;
  setAwayTeam: (t: Team) => void;

  setIsKnockout: (v: boolean) => void;

  evaluateAchievements: (input: AchievementEvalInput) => void;
  recordH2H: (homeId: string, awayId: string, homeScore: number, awayScore: number) => void;
  notifySave: () => void;
  setToastMsg: (msg: string | null) => void;
}

export function useCareerManager(params: UseCareerManagerParams) {
  const [careerState, setCareerState] = usePersistedState<CareerState | null>(
    'fp:career', null, { onPersist: params.notifySave }

  // handleStartCareer, handlePlayCareerMatch, handleCareerMatchResult,
  // handleProposeTrade, handleAdvanceSeason, ... mirror the *LeagueMatchResult /
  // *NextRound naming already used by useLeagueManager/useBracketManager
```

### Pattern 2: Adapter setter to reuse `useGameFlow` for career matches

**What:** `useGameFlow.ts` (verified, lines 42-70) writes match results directly into `setLeagueState`/`setBracketState` — both typed as plain `React.Dispatch<React.SetStateAction<LeagueState | null>>`. Since `CareerState.season.league` is itself a `LeagueState`, an adapter closure satisfying the same `Dispatch` signature lets `useGameFlow` be reused unmodified for career matches, instead of forking its logic.

**When to use:** Wiring career mode's in-match tactics/result flow without duplicating `useGameFlow`.

**Example:**
```typescript
// Source: derived from src/hooks/useGameFlow.ts's existing setLeagueState param type
const careerLeagueSetter: React.Dispatch<React.SetStateAction<LeagueState | null>> = useCallback(
  (updater) => setCareerState(prev => {
```

### Pattern 3: Progression math — reuse `generatePlayer()`'s formula, choose re-roll vs. nudge

**What:** `generatePlayer()` (verified, `src/data/leagues/generateTeam.ts` lines 36-57) computes `base = ovr - 7`, `spread = min(10, floor(ovr/8))`, then each attribute is `base ± rand(-spread, spread)` with positional boosts. This is a **full re-roll** — it discards whatever attributes the player had before and generates fresh ones centered on the new target OVR.

CONTEXT.md D-02 explicitly says to reuse `generatePlayer()` "pra recalcular atributos em direção a um novo OVR alvo" — read literally, this means calling `generatePlayer(id, name, number, pos, newTargetOvr)` again each season, which is the simplest possible implementation (zero new math) and satisfies D-02 as written. The tradeoff: a player's attribute *profile* (e.g., which specific attributes are high vs. low) gets fully re-randomized every season, only the target OVR determines the outcome — so a winger known for pace could season-to-season lose that identity even though the position stays the same.

**Two viable options for the planner (D-02 leaves the exact formula to Claude's Discretion):**

```typescript
// Source: pattern derived from src/data/leagues/generateTeam.ts generatePlayer()
// Option A — literal reuse (simplest, matches D-02's wording exactly):
function progressPlayer(p: Player, newTargetOvr: number): Player {
  return generatePlayer(p.id, p.name, p.number, p.position, newTargetOvr);
  // NOTE: attributes fully re-rolled; only id/name/number/position preserved
}

// Option B — proportional nudge (preserves attribute "shape"/identity):
function progressPlayer(p: Player, newTargetOvr: number): Player {
  const currentOvr = playerOvr(p);
  if (currentOvr === 0) return p;
  const scale = newTargetOvr / currentOvr;
  const nudge = (v: number) => Math.max(1, Math.min(99, Math.round(v * scale)));
  return {
    ...p,
    attributes: {
      speed: nudge(p.attributes.speed), stamina: nudge(p.attributes.stamina),
      passing: nudge(p.attributes.passing), finishing: nudge(p.attributes.finishing),
      tackling: nudge(p.attributes.tackling), dribbling: nudge(p.attributes.dribbling),
      vision: nudge(p.attributes.vision), positioning: nudge(p.attributes.positioning),
    },
  };
}
```

Retirement/replacement (D-02 "aposentadoria/substituição por jogador jovem gerado em idade avançada") maps cleanly onto **Option A's exact mechanism**: when a player is retired, call `generatePlayer()` fresh with a new id/name and a young-player target OVR — this is exactly what `generatePlayer()` was built for (it's already reused this way by `rosterSync.ts` for incoming transfers, verified at `src/services/rosterSync.ts` line 149).

### Anti-Patterns to Avoid
- **Re-deriving career rosters from `getLeague(id).teams` after season 1:** `rosterSync.ts`'s `syncLeagueRoster` (verified, line 200-232) always re-derives from `league.teams` (static data) when the user clicks "Atualizar elencos" on `TournamentSetupScreen`. If a career-mode `TournamentSetupScreen` instance ever calls this sync path against the static league instead of the career-evolved roster, an evolved/traded squad would be silently overwritten. Career mode must either hide the roster-sync button entirely when `isCareer`, or point it at a career-aware sync path.
- **Writing career cup state into `fp:bracketState`:** That key is already used by regular Copas mode (verified `useBracketManager.ts` line 36) and is *not* per-league (a single global key, disambiguated only by `bracketState.leagueId` at read time, per `App.tsx` lines 196-199, 231-234). Do not reuse it for career's cup — see Standard Stack / Alternatives Considered.
- **Treating `matchContext: 'league'` as sufficient to distinguish career from Campeonatos:** Both modes use the same underlying `LeagueState` shape and the same `SetupScreen`/`MatchScreen`, so `matchContext` alone can't tell `handleViewStatsFromMatch` (verified `App.tsx` lines 162-166) which handler set to call. See Common Pitfalls.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Player attribute synthesis toward a target OVR | A new random-attribute generator | `generatePlayer()` (`generateTeam.ts`) | Already calibrated (`base = ovr - 7` fix documented in ROADMAP.md as a "critical fix" for a prior OVR-deflation bug) — a second, uncalibrated implementation risks reintroducing that exact bug |
| League schedule / standings / bracket advancement for the career's season | New round-robin or bracket logic | `generateLeagueSchedule`, `computeStandings`, `createBracket`, `advanceBracket` (`tournament.ts`) | These are the same functions Campeonatos/Copas use today, fully tested (`tournament.test.ts`); career's season is explicitly "liga e copa rodando juntas... igual ao Campeonatos hoje já faz" (D-13) |
| localStorage read/write/reset-on-key-change | A new persistence hook | `usePersistedState` | Already solves the exact "swap key without remounting" problem (documented in its own source comment, lines 24-27) that a hand-rolled `useEffect(() => localStorage.setItem(...))` would have to re-solve |
| Fatigue recovery / post-match injuries for CPU teams during a career season | New fatigue/injury logic | `recoverFatigue`, `applyPostMatchInjuries` (`tournament.ts`) | Career's league rounds are structurally identical `LeagueFixture[][]` — no reason these differ from Campeonatos |

**Key insight:** Every mechanical piece career mode needs (schedule generation, standings, bracket, fatigue, injuries, CPU tactic variation, OVR-targeted attribute synthesis) already exists and is tested in this codebase. The actual net-new code is: (1) a thin wrapper type (`CareerState`) around existing shapes, (2) a progression function reusing `generatePlayer()`/`playerOvr()`, (3) a trade-evaluation function, (4) a reputation function, (5) UI screens. Resist the temptation to reimplement any of the four reused modules "career-flavored" — extend the wrapper, not the engine.

## Common Pitfalls

### Pitfall 1: `fp:bracketState` is a single global key, not per-league
**What goes wrong:** A career's national cup save collides with (or is silently overwritten by) an unrelated regular Copas save, or vice versa, if career cup state is ever written to `fp:bracketState`.
**Why it happens:** Verified in `useBracketManager.ts` (line 36): `usePersistedState<BracketState | null>('fp:bracketState', ...)` — no `{leagueId}` suffix, unlike `fp:leagueState:${leagueId}`. Disambiguation between leagues happens only at *read* time by comparing `bracketState.leagueId` against the currently selected league (`App.tsx` lines 196-199, 231-234), which only works because there is assumed to be at most one bracket in progress across the whole app at any time.
**How to avoid:** Give career's cup state its own storage path — embedded inside the new `fp:career` key (recommended, matches D-14's single-save-slot decision), never inside `fp:bracketState`.
**Warning signs:** A Copas save mysteriously resets after starting/advancing a career season, or a career's cup progress vanishes after playing a regular Copa.

### Pitfall 2: `Screen`/`MatchContext` union types are copy-pasted per hook file, not centralized
**What goes wrong:** Adding a new screen (e.g. `'career-home'`, `'season-end'`, `'trade-propose'`) or a new `MatchContext` value only in `useAppShell.ts` compiles cleanly even if `useResumePrompt.ts`, `useLeagueManager.ts`, `useBracketManager.ts`, and `useGameFlow.ts` (each of which independently redeclares its own local `Screen`/`MatchContext` type, verified across all four files) are never updated — TypeScript's contravariant function-parameter checking allows a wider-domain setter to satisfy a narrower-domain expected type, so the mismatch does not fail the build.
**Why it happens:** No shared `src/types/navigation.ts` (or similar) exists; each hook defines `type Screen = 'home' | 'select' | ... ` independently, and small differences already exist between them (e.g. `useLeagueManager.ts`'s `Screen` union lacks `'league-select'`/`'cup-select'` that `useBracketManager.ts`'s includes).
**How to avoid:** Either (a) extract a single shared `Screen`/`MatchContext` type used by every hook (a reasonable pre-cursor refactor for this phase, small and low-risk), or (b) if not refactoring, manually grep every file listed above whenever a new screen/context value is introduced and add it to each local union explicitly.
**Warning signs:** A new career screen navigates correctly from `App.tsx` but a `goHome`/resume-prompt/edit-tactics callback from an unrelated hook silently fails to type-check the new value and falls through an `else` branch at runtime.

### Pitfall 3: Recalculating all 6 leagues is fast — the localStorage *payload size*, not compute time, is the actual thing to watch
**What goes wrong (verified via benchmark, not theoretical):** Recalculating attributes for all 2,052 players (114 teams × 18 players across the 6 leagues) took **1.22ms** in a Node.js micro-benchmark run in this research session (see Sources for the exact script). Serializing a `CareerState`-shaped object holding all 6 leagues' full evolved rosters (114 teams, 2,052 players) to JSON took **1.56ms** to stringify and **1.79ms** to parse, producing a **~490KB** payload. This directly contradicts D-03's flagged concern — at current data scale, eager synchronous whole-league-set recalculation at every season transition is not a performance problem.
**Why the concern was reasonable to raise anyway:** Without a benchmark, "thousands of players, client-side, no backend" sounds expensive — it isn't, at this scale, because attribute recalculation is trivial arithmetic with no I/O per player.
**How to avoid over-engineering:** Do not build a Web Worker or incremental/lazy recompute system to solve a performance problem that doesn't exist. If lazy per-league recompute is still chosen, it should be justified by code simplicity (only touch the league in view) or genuine future-proofing (squad sizes/league count could grow), not performance — say so explicitly in the plan so a future reader doesn't assume it was performance-driven.
**Watch instead:** Total localStorage usage across ALL keys (`fp:career` ~490KB + up to 6× `fp:rosterCache:{id}` + `fp:achievements` + `fp:history` + `fp:h2h`, etc.) against browser quota (Safari private-mode ~5MB is the tightest common case) if the career mode is played for many (30+) seasons and `CareerState.history` grows unbounded — cap or summarize old history entries if this becomes a real concern, don't pre-optimize it now.

### Pitfall 4: `generatePlayer()` mutates identity, not just attributes, if called carelessly
**What goes wrong:** Calling `generatePlayer(newId, ...)` for progression (instead of reusing the player's existing `id`/`name`/`number`) creates what is effectively a brand-new player each season, breaking any UI or history that references a player by id across seasons (e.g. a "player of the season" history entry, or a traded player's post-trade identity per D-07).
**Why it happens:** `generatePlayer()`'s signature takes `id`/`name`/`number` as required params — it's designed for *creating* players (roster sync, initial generation), not for *updating* one in place. Passing the existing player's `id`/`name`/`number` through unchanged (as shown in Code Examples Option A) avoids this, but it's an easy detail to drop.
**How to avoid:** Always call `generatePlayer(p.id, p.name, p.number, p.position, newTargetOvr)` — never generate a new id for an existing player during progression; reserve fresh ids strictly for retirement replacements.
**Warning signs:** A traded or aged player "disappears" from squad lists that key off player id, or reappears as a duplicate.

```typescript
import { playerOvr } from '../utils/playerOvr';
import type { Player } from './types';

export function evaluateTradeOffer(
  offeredPlayer: Player,       // user gives this away
  requestedPlayer: Player,     // user wants this
  cpuSquad: Player[],
  managerReputation: number,
  rng: () => number = Math.random,
): { accepted: boolean; reason: string } {
  const offeredOvr = playerOvr(offeredPlayer);
  const requestedOvr = playerOvr(requestedPlayer);
  const ovrDelta = offeredOvr - requestedOvr; // positive = CPU gains value

  // Positional need: does the CPU squad have a surplus at the position it's giving up?
  const samePositionCount = cpuSquad.filter(p => p.position === requestedPlayer.position).length;
  const surplus = samePositionCount > 3; // squads carry ~5-6 per outfield position (generateTeam.ts quota)

  let acceptChance = 0.5 + ovrDelta * 0.04; // roughly ±4% per OVR point of value gained
  if (surplus) acceptChance += 0.15;
  acceptChance += Math.min(0.2, managerReputation * 0.002); // D-09: reputation nudges acceptance
  acceptChance = Math.max(0.02, Math.min(0.95, acceptChance));

  return { accepted: rng() < acceptChance, reason: ovrDelta >= 0 ? 'value-favorable' : 'value-unfavorable' };
}
```

Given `Player` already carries optional fields not used everywhere (`injuredRounds?`), adding `age?: number` directly to `Player` is the lower-friction, more consistent option.

   - Recommendation: Given `LeagueScreen` is in the "reused screens" spirit even though not explicitly named in D-12, extending it with an optional `onAdvanceSeason` prop (shown only when career + both league/cup done) is more consistent with the codebase's existing prop-driven reuse pattern (e.g. `TournamentSetupScreen`'s `mode` prop) than building a fully separate screen that duplicates the champion display.
