# Cross-AI Plan Review: Phase 4.4 — Modo Carreira

## 1. Summary

These seven plans form a well-researched, exceptionally detailed blueprint for building a multi-season career mode on top of an existing client-only React football simulator. The plans are grounded in direct codebase inspection, empirical benchmarks, and a clear understanding of the existing architecture's patterns (hook shapes, persistence keys, adapter setters). Dependency ordering is logical (Wave 1: engine + UI flags + type unification → Wave 2: hook P1 + screens → Wave 3: hook P2 → Wave 4: App.tsx wiring), and the research phase caught two critical risks (Pitfall 1: `fp:bracketState` key collision, Pitfall 2: `Screen` union drift across hooks) that the plans explicitly address. The overall design reuses existing infrastructure heavily, keeping the net-new surface small and focused.

**Overall Risk: MEDIUM**

---

## 2. Strengths

- **Empirical grounding**: The D-03 performance concern was benchmarked at ~1.2ms for 2,052 players rather than assumed — this directly prevented over-engineering a Web Worker or lazy-recompute system.
- **Precise integration-point awareness**: Plans 03 and 07 identify and fix the "Editar Táticas" navigation gap in `useGameFlow.handleStartMatch`, which RESEARCH.md correctly flagged as a silent TypeScript-passing bug that would strand users on wrong screens mid-career.
- **Persistence key isolation**: `fp:career` is a single new key with its own shape guard (`isValidCareerState`), completely isolated from `fp:leagueState:{id}`/`fp:bracketState` — avoids the collision documented in Pitfall 1.
- **Adapter-setter pattern**: The `careerLeagueSetter`/`careerBracketSetter` closures let `useGameFlow` be reused unmodified for career matches, avoiding duplicated match-result logic across two modes.
- **Self-contained engine**: `src/engine/career.ts` is pure functions with injectable RNG — fully unit-testable, no React dependency, matching the existing `tournament.ts` pattern exactly.
- **Manual verification task**: 04.4-07 Task 4 is a 10-step human checkpoint for real-browser behavior that no jsdom test can validate (D-03 real perf, "Editar Táticas" round-trip, visual gate on advance-season button).
- **Trade cap enforced at multiple layers**: `canProposeTrade()` in the engine + guard in `handleProposeTrade` + UI-level disable in `CareerHubScreen` + blocked UI in `TradeProposalScreen` — defense in depth against an invariant violation.

---

## 3. Concerns

### HIGH Severity

- **`evaluateTradeOffer` acceptance ceiling at 0.95 makes the "forced acceptance" test technique brittle.** 04.4-06 Task 3's test for D-06 (trade cap) says "force acceptance via a deterministic favorable offer" but with `acceptChance = Math.max(0.02, Math.min(0.95, ...))`, no offer is truly guaranteed. Even at max clamp, `rng() < 0.95` fails ~5% of the time. A retry loop with a seeded RNG sequence where you know the exact values could work, but this isn't specified. The test could flake.

- **`progressAllLeagues` in `handleAdvanceSeason` is called synchronously inside a React state update.** While the benchmark shows ~1.2ms for the math itself, this call happens inside `setCareerState`'s updater function (via `useCallback`), which runs during React's synchronous render phase. The benchmark was in isolation — inside a live React render with ~490KB of serialized state, the full `setCareerState` call including the spread-over-6-leagues operation plus React's reconciliation of the new `careerState` reference could be slower than the raw math benchmark. The 04.4-07 manual verification Task 4 step 8 checks for this, but a synchronous setState doing heavy computation is worth flagging.

- **`generateRandomName` may produce colliding player names.** The plan says "no uniqueness tracking needed (this is for a single retirement replacement at a time)" — this is true for the initial implementation, but over many seasons with multiple retirements per team across 6 leagues (114 teams × ~2 retirements per season), the probability of duplicate names rises. This is cosmetic (player IDs uniquely identify them), but the plan should acknowledge that name collisions will accumulate over deep careers.

### MEDIUM Severity

- **`TournamentSetupScreen` manager-name sanitization uses inline regex but no debounce.** The plan strips `[\x00-\x1F\x7F]` and caps to 24 chars on every `onChange`. This is correct but fires on every keystroke — for a simple text input this is fine, but the plan says to also call `setManagerName(sanitize(e.target.value))` which triggers a re-render per keystroke. Trivial perf, but worth noting the input has no debounce.

- **`handleAdvanceSeason` uses `getLeague(careerState.leagueId)!` to rebuild the league definition for season N+1, but `getLeague` returns static data.** After multiple seasons of progression, `createCareerSeason` is called with `evolvedRosters[careerState.leagueId]` as the team list, not the static league data — this is correct. But the `LeagueDefinition` (cup name, league name, `relegationSpots`, `europeanSlots`) comes from the static `getLeague()` call, which is fine since those fields are cosmetic/label data. Worth noting as implicit assumption.

- **`CareerHubScreen`'s `onAdvanceSeason` button is gated on `phase === 'done'` AND `stage === 'champion'`, but `cup.stage` can also be `stage` where user got eliminated earlier (e.g. user lost in quarterfinals — the bracket is still fully resolved since every match was simulated/played, so stage reaches `'champion'` with `championId` set to some other team).** The plan correctly says both must be terminal — `stage === 'champion'` is correct here (it means the bracket has a champion, not necessarily the user). But this is a subtle point the acceptance criteria don't explicitly validate.

- **No test for `deriveCupResult` returning correct values when the user has been eliminated.** The 04.4-01 acceptance criteria say `deriveCupResult` returns `'roundOf16'` when the user's only played match is there and they lost — but what about `'quarterfinal'`, `'semifinal'`, `'runner-up'`? The contract requires these but only tests one branch.

- **`Screen` union duplication persists across 5 files.** Plan 03 manually adds the 5 new career literals to each file's local union rather than extracting a shared type. The plan acknowledges this is a mechanical workaround, not a fix, and documents it clearly. But it's a maintenance risk for the next phase — any future screen value must again be added to 5 files manually.

### LOW Severity

- **`careerState?.season.league` null checks throughout `useCareerManager`.** The handlers all guard on `if (!careerState) return;` — good. But the league-leg handlers also access `careerState.season.league` without a separate null check on `.season.league` within the guard body, relying on the `useCallback` closure capturing a stable `careerState` reference. This is correct given the guard, but if `careerState` is `null`-checked at the top and the handler is called synchronously (which it is from App.tsx callbacks), no intermediate null can appear. Fine, but implicit.

- **`notifySave` passed to `useCareerManager` but the plan doesn't explain what `notifySave` does in the existing codebase.** The Research doc confirms it's from `usePersistedState`'s `onPersist` callback — it's a toast notification to the user that the save happened. This is fine, but a reviewer unfamiliar with the codebase wouldn't know this.

- **`SeasonEndScreen` imports `getLeague` to look up the champion team's crest from `entry.leagueChampionId`, but `CareerSeasonHistoryEntry` only stores an ID.** In a career where the champion is a team from a progressed roster (not the static league), the crest/name lookup via `getLeague()` still works since team identities (id, name, crest, colors) don't change during progression — only squad attributes do. This is correct but implicit.

## 4. Suggestions

- **Add seeded-RNG acceptance tests for `evaluateTradeOffer`.** Instead of relying on the retry loop mentioned in 04.4-06 Task 3, create a deterministic test with a fixed seed where you know the exact RNG sequence values ahead of time. For example: use `seededRng(42)` and assert acceptance on specific call numbers where you know `rng() < acceptChance`. This eliminates flakiness entirely.

- **Consider moving `progressAllLeagues` out of the `setCareerState` updater.** Instead of computing evolved rosters inside the setState callback, compute them into a local variable first, then pass the already-evolved rosters into setState. This keeps heavy computation out of React's synchronous render phase and makes the benchmark a better approximation of real browser perf (since the computation happens between renders, not during one).

- **Add a `deriveCupResult` unit test covering all 6 return values.** The 04.4-01 acceptance criteria only verify `'champion'` and `'roundOf16'` — add tests for `'runner-up'`, `'semifinal'`, `'quarterfinal'`, and `'not-played'` paths.

- **Document the duplicate-name risk in `generateRandomName`.** Add a comment in the function or in the plan summary noting that over many seasons, name collisions are possible (and cosmetic only since player IDs are unique). This prevents a future developer from treating it as a bug.

- **Add a `careerState.season.league` null-guard inside league-leg handlers after the top-level `!careerState` guard.** While the current code is correct given synchronous handler invocation, a defensive `if (!careerState?.season?.league) return;` adds clarity and prevents a future async refactor from introducing a race condition.

- **For the shared `Screen` union problem, create a ticket/backlog item for 04.4 completion.** After Phase 4.4 lands, extracting `Screen`/`MatchContext` into a shared `src/types/navigation.ts` is a low-risk, high-value cleanup that prevents the Pitfall 2 problem from recurring in Phase 4.5. The plans correctly note this but don't schedule it.

## 5. Risk Assessment

**Overall Risk: MEDIUM**

**Justification:** The phase has zero new external dependencies, zero new network calls, and reuses thoroughly-tested existing engine functions (`generateLeagueSchedule`, `computeStandings`, `createBracket`, etc.) verbatim. The architectural risks flagged in the Research phase (Pitfall 2's union drift, Pitfall 1's key collision) are explicitly addressed with concrete mitigations. The single biggest concern — D-03's performance — was empirically debunked before planning began.

The remaining risks are all manageable:
- Test flakiness from the 0.95 acceptance ceiling on `evaluateTradeOffer` (fixable with seeded-RNG assertions).
- Synchronous heavy computation inside a setState updater (fixable by hoisting the computation to a local variable before setState is called).
- No existing hook test infrastructure for `useCareerManager` (the plan acknowledges this and establishes a new `renderHook` pattern following the existing `useMatchSimulation.test.ts` precedent).

The plans are unusually thorough and codebase-grounded for an AI-generated plan set. The dependency ordering is sound, the manual verification task catches what automated tests can't, and the engine/UI/hook separation means each plan can be verified independently before integration.
